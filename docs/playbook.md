# Solution Sourcing Kit — Playbook

This playbook defines the end-to-end process for the Solution Sourcing Kit (Layer 3). It covers how to move from a frozen Discovery PRD to a sourcing decision that routes the initiative to the Engineering Execution Kit with clear Build/Buy/Adopt intent.

---

## Artifact Flow

```
Upstream: Frozen DPRD from Product Intelligence Kit (Layer 2)
         │
         ▼
Step 0: Pre-Flight — Confirm DPRD frozen, ER exists
         │
         ▼
Step 1: Sourcing Options Evaluation Record (SOER) — human-authored
         │ Validate → Freeze
         ▼
Step 2: Vendor/Solution Evaluation Record (VER) — generated
         │ Validate → Freeze
         ▼
Step 3: Sourcing Decision Record (SDR) — generated (human provides decision)
         │ Validate → Freeze
         ▼
Step 4: Handoff to Layer 4 (Engineering Execution Kit)
```

---

## Upstream Interface

**Upstream:** Product Intelligence Kit (Layer 2)
**Input:** Frozen DPRD

| Artifact | What SSK Uses It For |
|----------|---------------------|
| DPRD (frozen) | Requirements baseline for sourcing option evaluation; functional fit assessment |

If the DPRD is not frozen, do not begin the sourcing evaluation. Request a frozen DPRD from the upstream product team.

---

## Step 0 — Pre-Flight

Before beginning SSK work:

1. **Confirm the DPRD is frozen.** If the DPRD status is not Frozen, stop. Return to PIK.
2. **Confirm the Engagement Record exists.** If there is no ER for this initiative, create one at `docs/engagement/er-{initiative}.md` in the consuming project using the ER template from `aieos-governance-foundation/docs/engagement-record-template.md`.
3. **Evaluate the fast-path.** If Build is obviously the correct sourcing approach (no market alternatives exist, the capability is unique to the organization's domain, or the capability is a competitive differentiator), SSK may be skipped:
   - Document the fast-path justification in the EEK Kit Entry Record (KER) when entering Layer 4.
   - The KER must explicitly state why sourcing evaluation was unnecessary.
   - Proceed directly to EEK with the frozen DPRD.

If the fast-path does not apply, proceed to Step 1.

---

## Step 1 — Sourcing Options Evaluation Record

**Artifact:** Sourcing Options Evaluation Record (SOER)
**Type:** Human-authored entry gate
**Spec:** `docs/specs/soer-spec.md`
**Template:** `docs/artifacts/soer-template.md`
**Validator:** `docs/validators/soer-validator.md`

### Purpose

The SOER identifies candidate sourcing options mapped against DPRD requirements. It ensures the organization has considered viable alternatives before committing to a sourcing approach. The SOER is not generated by AI — the sourcing evaluator completes it based on market research and organizational context.

### Inputs
- Frozen DPRD from the Product Intelligence Kit
- Market research on available commercial products and open-source solutions
- Organizational constraints (budget, timeline, compliance requirements, existing technology stack)

### Process

1. The sourcing evaluator obtains the frozen DPRD and reviews the requirements.
2. Using the SOER template, the evaluator identifies candidate sourcing options:
   - **Build options:** Custom development approaches (greenfield, brownfield, platform extension)
   - **Buy options:** Commercial products that address the DPRD requirements (name specific vendors/products)
   - **Adopt options:** Open-source solutions that address the DPRD requirements (name specific projects)
3. For each option, the evaluator documents: option description, preliminary cost estimate, preliminary risk assessment, and functional coverage against DPRD requirements.
4. The evaluator identifies which options merit detailed evaluation in Step 2 (shortlist).
5. The completed SOER is validated in a separate session from the one that completed it.
6. On PASS: the sourcing evaluator reviews and freezes the SOER. **No VER generation may begin until the SOER is Frozen.**
7. On FAIL: address blocking issues and re-validate.

### Freeze Points
- SOER must be Frozen before VER generation begins

---

## Step 2 — Vendor/Solution Evaluation Record

**Artifact:** Vendor/Solution Evaluation Record (VER)
**Type:** Generated
**Spec:** `docs/specs/ver-spec.md`
**Template:** `docs/artifacts/ver-template.md`
**Prompt:** `docs/prompts/ver-prompt.md`
**Validator:** `docs/validators/ver-validator.md`

### Purpose

The VER provides a structured comparison of shortlisted candidates from the SOER. It evaluates each candidate on total cost of ownership, risk profile, functional fit, integration complexity, and long-term viability. The VER does not make the decision — it provides the evidence base for the human decision in Step 3.

### Inputs
- Frozen SOER (shortlisted candidates)
- Frozen DPRD (requirements baseline)
- Vendor/solution documentation, pricing, and technical specifications
- Organizational sourcing principles (`docs/principles/sourcing-principles.md`)

### Process

1. In a new AI session, provide: frozen SOER + frozen DPRD + vendor/solution documentation + `docs/specs/ver-spec.md` + `docs/artifacts/ver-template.md`. Use the VER prompt (`docs/prompts/ver-prompt.md`).
2. Review the generated VER. Check that all shortlisted candidates from the SOER are evaluated, scoring criteria are applied consistently, and integration complexity is assessed for each non-Build option.
3. Validate the VER in a separate session using `docs/validators/ver-validator.md` and the spec.
4. On PASS: human review and freeze. **The frozen VER is now the authoritative evaluation evidence.**
5. On FAIL: address blocking issues and re-generate or correct; re-validate.

### Freeze Points
- VER must be Frozen before SDR generation begins
- Frozen VER is immutable; changes require re-entry protocol

---

## Step 3 — Sourcing Decision Record

**Artifact:** Sourcing Decision Record (SDR)
**Type:** Generated (human provides the decision, AI generates the formal record)
**Spec:** `docs/specs/sdr-spec.md`
**Template:** `docs/artifacts/sdr-template.md`
**Prompt:** `docs/prompts/sdr-prompt.md`
**Validator:** `docs/validators/sdr-validator.md`

### Purpose

The SDR is the terminal artifact. It formally records the sourcing decision (Build, Buy, or Adopt), the rationale grounded in VER evidence, and the downstream implications for the Engineering Execution Kit. The human makes the decision; the AI generates the formal documentation.

### Inputs
- Frozen VER (evaluation evidence)
- Frozen SOER (options considered)
- Frozen DPRD (requirements baseline)
- Human-provided sourcing decision: Build, Buy (naming the selected vendor/product), or Adopt (naming the selected OSS project)
- Human-provided decision rationale (why this option over the alternatives)

### Process

1. The sourcing evaluator reviews the frozen VER and makes the sourcing decision.
2. In a new AI session, provide: frozen VER + frozen SOER + frozen DPRD + the human decision and rationale + `docs/specs/sdr-spec.md` + `docs/artifacts/sdr-template.md`. Use the SDR prompt (`docs/prompts/sdr-prompt.md`).
3. Review the generated SDR. Confirm the decision is accurately recorded, the rationale references VER evidence, and downstream implications are documented.
4. Validate in a separate session using `docs/validators/sdr-validator.md` and the spec.
5. On PASS: sourcing evaluator and project lead review and freeze.
6. On FAIL: address blocking issues; re-generate or correct; re-validate.

### Decision Values

| Decision | Meaning | What Happens Next |
|----------|---------|-------------------|
| Build | Custom development is the best sourcing approach | Full EEK flow — greenfield or brownfield engineering |
| Buy | A commercial product best meets the requirements | Integration-scoped EEK flow — vendor integration, configuration, adapter development |
| Adopt | An open-source solution best meets the requirements | Integration-scoped EEK flow — OSS integration, customization, wrapper development |

### Freeze Points
- SDR must be Frozen before handoff to EEK
- A frozen SDR is the sourcing clearance for engineering entry

---

## Step 4 — Downstream Handoff

**Downstream:** Layer 4 (Engineering Execution Kit)
**Handoff artifacts:** Frozen DPRD + Frozen SDR

The handoff provides:
- The frozen DPRD (what to build/integrate)
- The frozen SDR (how it is being sourced)
- SDR §Sourcing Decision: Build, Buy, or Adopt
- SDR §Downstream Implications: scope guidance for EEK based on the sourcing decision

### Routing

| SDR Decision | EEK Scope |
|--------------|-----------|
| Build | Full EEK flow. The PRD is derived from the DPRD. Architecture, design, and implementation cover the full system. |
| Buy | Integration-scoped EEK. Architecture and design focus on vendor integration: adapters, configuration, data migration, and custom extensions. |
| Adopt | Integration-scoped EEK. Architecture and design focus on OSS integration: wrappers, customization, contribution strategy, and maintenance plan. |

EEK receives the SDR alongside the DPRD. The KER (Kit Entry Record) in EEK must reference the SDR and acknowledge the sourcing decision.

## Freeze Points Summary

| Artifact | When Frozen | What It Gates |
|----------|------------|---------------|
| SOER | Before VER generation | VER generation |
| VER | After validation | SDR generation |
| SDR | After validation | EEK entry (Layer 4 handoff) |

## Session Discipline

Follow these rules in every AI session:

| Rule | Why |
|------|-----|
| One artifact per session | Prevents context contamination across artifacts |
| Separate generation and validation sessions | Prevents self-validation bias |
| Include full frozen upstream artifacts | Do not summarize; the AI needs complete context |
| Include spec and template for generation sessions | The AI generates against the spec, not from memory |
| Include spec and validator for validation sessions | The validator judges against the spec, not against the generated content |

Do not ask the AI that generated an artifact to also validate it in the same session.

---

## Re-Entry Protocol

When a frozen artifact must be corrected:

1. Identify the artifact to be changed (SOER, VER, or SDR).
2. Identify all downstream artifacts that reference it or depend on it.
3. Assess the impact: does the change affect options considered, evaluation scores, or the sourcing decision?
4. Issue a new version of the artifact (e.g., VER v2, SDR-PROJECT-001v2).
5. Re-validate the new version.
6. Re-validate all affected downstream artifacts that reference the changed artifact.
7. Document the change in the new version's document control section with a reference to the original and the reason for the correction.

---

## Abort Protocol

If the pre-flight check (Step 0) reveals that the DPRD is not frozen:

1. Do not proceed with SOER completion.
2. Contact the upstream product team and request a frozen DPRD.
3. Hold SSK intake at the pre-flight step until the DPRD is frozen.

If sourcing evaluation reveals that no viable options exist (Build is infeasible and no Buy/Adopt candidates exist):

1. Document the finding in the SOER.
2. Escalate to the project sponsor. This may require returning to PIK to adjust the DPRD scope.
3. Do not proceed to VER with an empty candidate set.

---

## Amendment Procedure

A frozen artifact may be corrected in place without re-validation when **all** of the following criteria are met:

1. The correction does not affect any field evaluated by a hard gate.
2. The correction does not change scope, decisions, options, scores, or technical specifications.
3. The correction does not affect any field referenced by a downstream artifact.

**Procedure:** Make the correction and add an Amendment Log entry to the artifact's Document Control section: date, what changed, materiality criterion cited, and who authorized the change. No re-validation is required.

**If there is any ambiguity** about whether a change is non-material, treat it as material and issue a new artifact version. The amendment path must not become a workaround for the version protocol.

## Maintaining the Engagement Record

The Engagement Record (ER) is a project-level artifact that lives in the consuming project at `docs/engagement/er-{initiative}.md`. It spans all AIEOS layers and is maintained by each kit's operators as work passes through. The ER spec and format are defined in `aieos-governance-foundation/docs/engagement-record-spec.md`.

**SSK maintains the Layer 3 section (§3a) of the ER.**

### What to Update During Sourcing Operations

| Trigger | ER update |
|---------|-----------|
| SSK entered | Confirm ER exists; create if needed |
| SOER frozen | Add SOER ID to artifact table |
| VER frozen | Add VER ID to artifact table |
| SDR frozen | Add SDR ID to artifact table; record sourcing decision (Build/Buy/Adopt) in Notes column |
| SSK skipped (fast-path) | Note fast-path justification; reference KER where skip is documented |
| Key decision made | Record in §3a Key Decisions (e.g., shortlisting criteria, evaluation weighting rationale) |
